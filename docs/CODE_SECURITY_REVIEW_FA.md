# بررسی ساختار، کارایی و امنیت کد

تاریخ: ۲۰۲۶-۱۰-۲۴. مبنا: وضعیت فعلی فایل‌های پروژه، شامل تغییرات ثبت‌نشده پیشین.

این بررسی شامل مطالعه کد، تنظیمات Docker و اجرای آزمون‌های مشخص در محیط توسعه است؛ آزمون نفوذ کامل، ممیزی تمام وابستگی‌ها برای CVE و تأیید آمادگی تولید انجام نشده است. داده‌های عملیاتی یا منابع خارجی تغییر داده نشدند. آزمون‌های دارای نوشتن دیتابیس با rollback پایان یافتند؛ آزمون HTTP یک نشست ورود مدیر ایجاد کرد.

## یافته‌ها و اصلاحات انجام‌شده

### ۱. محافظت و یکپارچگی خروجی CSV — اهمیت متوسط، اصلاح شد

در `purchase_reports/service.py` محافظت قبلی فقط چهار پیشوند ASCII را بررسی می‌کرد. پیشوندهای تمام‌عرض و بعضی نویسه‌های کنترلی پوشش کامل نداشتند. خروجی اقدامات در `www/portal.html` نیز فاصله پیش از فرمول، newline و نمونه‌های تمام‌عرض را پوشش نمی‌داد.

تابع مستقل `csv_safety.safe_csv_cell` اضافه شد و خروجی خرید از آن استفاده می‌کند. پیشوندهای خطرناک متنی محافظت می‌شوند؛ اعداد واقعی و رشته‌های عددی متناهی مانند مقدار منفی حفظ می‌شوند. خروجی اقدامات نیز به endpoint سرور دارای POST، CSRF و تطبیق مجدد شناسه‌ها با محدوده مجاز منتقل شد؛ منطق محافظت تکراری مرورگر حذف شد. آزمون تبدیل رفت‌وبرگشت CSV با جداکننده‌ها و نویسه‌های کنترلی اجرا شد. اجرای خودکار فایل در Excel یا LibreOffice آزمایش نشده است. آپاستروف یک دفاع اولیه است و رفتار ذخیره و بازگشایی همه نرم‌افزارها را تضمین نمی‌کند؛ برای تبادل حساس، XLSX با سلول‌های متنی صریح مناسب‌تر است.

مرجع: [OWASP CSV Injection](https://community.owasp.org/attacks/CSV_Injection).

### ۲. ستون تکراری و پردازش غیرضروری ورودی CSV — اهمیت متوسط، اصلاح شد

در `imports.py`، `DictReader` برای سرستون تکراری مقدار قبلی را بی‌صدا جایگزین می‌کرد. همچنین تمام سطرها پیش از بررسی سقف ۲۰۰ سطر در حافظه ساخته می‌شدند. اکنون سرستون تکراری رد می‌شود، خواندن به ۲۰۱ سطر محدود است و نوع ورودی پیش از encode بررسی می‌شود. سقف قبلی یک مگابایت همچنان برقرار است. این تغییر ابهام داده و پردازش اضافی را کاهش می‌دهد؛ مدرکی از دور زدن مجوزها با این ورودی مشاهده نشد.

### ۳. فایل‌های خصوصی در زمینه ساخت Docker — اهمیت متوسط، اصلاح شد

`.gitignore` مانع ارسال فایل به Docker builder نمی‌شود. `.dockerignore` قبلاً `.local`، secrets، sites، volumes و فایل‌های کلید را صریحاً حذف نمی‌کرد. این موارد و فایل اتصال منابع به استثناهای ساخت اضافه شدند. Dockerfile فعلی فقط مسیرهای مشخص را کپی می‌کند؛ این یافته به معنای اثبات وجود رمز در image فعلی نیست. در مرحله تکمیلی، ساخت کامل image تولید و بررسی آفلاین آن موفق شد.

### ۴. بارگذاری تکراری اسناد و نام کاربران — کارایی، اصلاح شد

داشبورد پس از دریافت فهرست اقدامات، سند هر اقدام را برای تشخیص خروجی خودکار و دوباره برای بررسی مجوز می‌خواند؛ نام مسئول و تکمیل‌کننده نیز به‌صورت تکی بازیابی می‌شد. اکنون سند هر اقدام در همان درخواست بازاستفاده می‌شود و نام‌های موردنیاز با یک خواندن گروهی دریافت می‌شوند. اطلاعات کاربران همچنان فقط از شناسه‌های موجود در اقدامات مجاز انتخاب می‌شود. آزمون عدم خواندن تکراری سند و جداسازی داده آزمایشی موفق بود. هنوز برای هر اقدام یک سند خوانده می‌شود؛ حذف کامل این الگو به بازطراحی کنترل مجوز و سنجش کارایی نیاز دارد. بنچمارک زمان پاسخ انجام نشد.

## تکمیل اصلاحات ساختاری

1. **آزمون‌های ناسازگار اصلاح شدند.** تأیید گزارش از مسیر واقعی بررسی انجام می‌شود و تأیید مستقیم همچنان رد می‌شود. آزمون HTTP با فهرست واقعی حوزه‌ها و سقف API تطبیق داده شد؛ نشست خودش را با CSRF می‌بندد.
2. **مرزهای سرویس جدا شدند.** `api.py` فقط مسیرهای عمومی سازگار را نگه می‌دارد. حساب، عضویت و اقدامات در سه ماژول services قرار دارند. استخراج/محاسبه و نگهداری snapshot موجودی نیز به workflow_data و workflow_storage منتقل شدند. فراخوانی HTTP مستقیم سرویس‌های داخلی در آزمون رد شد.
3. **خوانایی بخش‌های حساس بهبود یافت.** reviews، workflow، منابع اتصال، API، سرویس‌ها و آزمون‌های اصلی قالب‌بندی شدند. lint و بررسی قالب در CI اضافه شد؛ نحو تمام Pythonها، JavaScriptهای public و اسکریپت داخلی داشبورد بررسی می‌شود. استانداردسازی قالب تمام ماژول‌های قدیمی هنوز تدریجی است.
4. **حساب‌های واقعی از آزمون‌های بررسی و منابع انسانی حذف شدند.** کاربران و حوزه‌های موقت با شناسه تصادفی ساخته و rollback می‌شوند. نام سایت و مسیر bench از محیط یا تنها سایت نصب‌شده تشخیص داده می‌شوند. تطبیق مسئول پایش با نام کامل فرد حذف و تنظیم صریح با fallback یکتای برنامه‌های موجود جایگزین شد.
5. **محافظت CSV در سرور مشترک شد.** خروجی اقدامات و خرید از یک تابع استفاده می‌کنند؛ درخواست خروجی اقدامات دوباره مجوز و فیلتر را کنترل می‌کند.
6. **تصاویر و وابستگی‌های مستقیم تثبیت شدند.** Dockerfile و Composeها digest مشخص دارند؛ نسخه jdatetime، python-tds و pyOpenSSL دقیق است. commit متناظر Frappe نیز هنگام ساخت بررسی می‌شود. نسخه ۱۳۴ وابستگی نصب‌شده محیط موفق Linux/Python 3.14 در constraints-runtime.txt ثبت و به uv و pip هنگام ساخت اعمال می‌شود؛ این فایل hash دانلود بسته‌ها و وابستگی‌های ابزار ساخت را قفل نمی‌کند. لایه نصب framework از کد برنامه جدا شده تا تغییر برنامه نیازمند نصب مجدد Frappe نباشد.
7. **TLS قابل تنظیم و اجباری در پیکربندی تولید شد.** اعتبارسنجی CA و نام میزبان برای هر دو driver اضافه شد؛ SQL Server رمزنگاری تمام نشست دارد و MySQL تنزل اتصال به سوکت بدون TLS را پیش از پرس‌وجو رد می‌کند. نبود CA در حالت سخت‌گیرانه موجب رد اتصال است. اتصال فعلی توسعه خودکار تغییر نکرده است.

راهنمای اجرای آزمون‌ها، تنظیم مسئول و نمونه اتصال: [SECURE_CONFIGURATION_FA.md](SECURE_CONFIGURATION_FA.md).

## نکات امنیتی نیازمند اعتبارسنجی عملیاتی

- APIهای تغییردهنده بررسی‌شده به POST محدودند و endpoint مهمان در جست‌وجوی whitelistها دیده نشد. این مشاهده جایگزین ممیزی کامل احراز هویت و CSRF چارچوب نیست.
- `ignore_permissions=True` در سرویس‌های لازم حفظ شده است. آزمون منفی واقعی برای عملیات عضویت، نقش منابع انسانی، ثبت موجودی، تنظیمات، کاتالوگ، پیشرفت، CSV و واگذاری بررسی با نقش مهمان، کارمند، حوزه دیگر، مدیر واحد و منابع انسانی اضافه و موفق شد. پوشش این آزمون‌ها به معنای اثبات امنیت تمام APIهای چارچوب نیست.
- اتصال MySQL در کد تراکنش خواندنی دارد؛ اتصال SQL Server از `readonly=True` استفاده می‌کند. مجوز واقعی فقط‌خواندنی باید روی حساب پایگاه منبع اعمال و کنترل شود؛ گزینه اتصال به‌تنهایی اثبات محدودیت حساب نیست.
- پشتیبانی TLS و سیاست تولید در کد اضافه و با mock آزموده شد. گواهی معتبر سرورهای واقعی، وضعیت رمزنگاری واقعی شبکه و مجوز حساب‌های منبع هنوز باید در محیط استقرار تأیید شوند؛ اطلاعات این سرورها در اختیار این تغییر نبود.
- فراداده تنظیمات جاری بدون چاپ میزبان، شناسه اتصال یا رمز بررسی شد: فایل اتصال mode 0600 دارد و مسئول پایش صریحاً تنظیم شده است. برای هیچ‌یک از دو منبع CA و TLS در تنظیمات اتصال تعریف نشده و حالت سخت‌گیرانه توسعه فعال نیست. برای فعال‌سازی واقعی، گواهی معتبر سرورها باید فراهم شود. حفاظت backup و گردش رمزها بررسی نشد.
- پورت وب در هر دو Compose به loopback محدود است و دیتابیس پورت عمومی ندارد. HTTPS، reverse proxy و تنظیمات امنیتی تولید باید در استقرار نهایی آزمایش شوند؛ پروژه فعلاً تأیید تولید ندارد.

## اعتبارسنجی نهایی

مجموعه کامل `docker/run-regressions.py --http`: **۱۸ از ۱۸ بررسی موفق**؛ شامل ۱۵ اسکریپت و سه smoke check. آزمون‌های محاسبه شامل ۱۱ آزمون خرید و ۷ آزمون ریاضی موجودی‌اند.

پوشش موفق: مجوز بین حوزه‌ها، ماتریس نقش‌های واقعی، گردش مرخصی/مأموریت و تأیید انسانی، واگذاری و لغو، نسخه‌های غیرقابل‌تغییر موجودی، داده خودکار بدون تأیید انسانی، کاتالوگ، تنظیمات، اکسل، پیش‌نمایش ورود، CSV، قرارداد TLS و بسته شدن اتصال.

پس از آن، آزمون HTTP توسعه‌یافته خروجی CSV با CSRF و منع HTTP مستقیم سرویس داخلی نیز موفق شد. کنترل lint/format، نحو تمام Pythonها و JavaScriptهای public و داشبورد، `pip check`، اعتبار Compose توسعه/تولید با متغیرهای لازم و `git diff --check` موفق بودند.

دو شکست قبلی `smoke.extended` و `http_smoke.run` رفع شده‌اند. اجرای واقعی GitHub Actions، آزمون بار، تست نفوذ کامل و TLS روی منابع واقعی انجام نشده‌اند. `pip check` ممیزی CVE نیست.

ساخت نهایی image `saeenaria-portal:review-check` با موفقیت کامل شد. خطای موقت دانلود PyPI با cache و تلاش مجدد برطرف شد و اعتبارسنجی TLS غیرفعال نشد. اجرای آفلاین داخل همین image، کاربر غیرریشه، کتابخانه native دیتابیس، پشتیبانی TLS در SQL Server، import سرویس‌ها، assets و تطابق تمام ۱۳۴ نسخه constraints را تأیید کرد. `pip check` داخل image نیز موفق بود. راه‌اندازی انتها به انتهای Compose تولید، reverse proxy و TLS منابع واقعی هنوز انجام نشده‌اند. هیچ سرویس جاری با image جدید جایگزین نشده است.
